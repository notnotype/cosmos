## 问题

### 维护者的原话（未改写）

> UI方面还有一个严重的问题：文案太过于专业化，让用户有所疑惑。UI文案可以专业，但不能太专业，必须保证大部分正常用户能够一眼看懂。

### 为什么这句话现在还不能直接照着做

它是对的，但没有边界。「专业但不能太专业」「大部分正常用户能一眼看懂」——这两句都无法判定「这个按钮现在算过线了吗」。没有判据就直接改文案，会变成三件坏事：

1. **无边界改写**：每次动 UI 都顺手改几句，改到哪算哪，评审没有依据，最后没人能说清标准是什么。
2. **改两遍**：界面职责重划（[`ui-surface-ownership-v1.md`](ui-surface-ownership-v1.md)）会删掉一大批表单和区块，那些文案会连人带字一起消失。先改文案等于白改。
3. **改坏自动化**：浏览器验收里有大量断言是**按界面文字定位**的（见[影响](#影响)），文案改了不改定位器，测试直接红——而测试红的表象会被误读成功能回归。

所以这份 Proposal 要交付的不是「一批更好的文案」，而是**一套能判定、能执行、能验收的标准**，以及一条有起点和终点的实施路径。

### 一个关键发现：规则其实已经有了

「不要暴露用户看不懂的内部概念」不是新政策，仓库里已经有两处写明：

- 根 [`AGENTS.md`](../../AGENTS.md)：「面向用户的文字写用户能做什么，解释必要术语、限制、回退和未验证部分，**不暴露无上下文的内部实现名**」。
- [`CONTEXT.md`](../../CONTEXT.md) §核心语言与「当前命名结论」：已经给用户可读的最小单元定名「信息条目 / Entry」、长期聚合定名「话题 / Topic」、展示角色定名「热点 / Spotlight」，并明确「Workspace」在**界面**按 kind 显示「栏目」「专题」「学习计划」或「工作区」。

也就是说：仓库已经决定过「内部用哪个词、界面用哪个词」这件事，只是从来没有把它落实到界面文案上。本 Proposal 是把已有规则执行到 UI，不是新立一套政策——这一点很重要，它意味着大部分文案改动**没有产品歧义**，只有少数几个词需要你裁定。

逐屏取证原文已移至分册[「当前行为与证据」](ui-copy-review-v1/part-current-behavior-evidence.md#当前行为与证据)。

## 目标与非目标

### 目标

1. **给判据**：「专业但不过度专业」落成几条能被人和 Agent 同时使用的判定规则，能指出某句文案没过线、以及过的是哪条线。
2. **给范围**：说清哪些文案在范围内、哪些不在，避免污染日志、错误码和开发者界面。
3. **给实施路径**：分批、可验收、能回滚，且与界面职责重划不互相覆盖。
4. **给归属**：新词由谁定、定在哪、怎么保证 agent 不即兴造词。

### 非目标

- 不重写产品定位、宣传语或首页叙事（那是产品文案，不是 UI 文案）。
- 不改日志、API 错误码与消息格式、`docs/` 文档正文（这些面向的是排障者，术语密度本来就该高）。
- 不改 `/dev/components` 开发者组件实验室（它的读者是开发者）。
- 不做多语言/国际化框架（当前只有中文界面，引入 i18n 是另一件事）。
- 不改变任何功能行为；文案改动导致的界面结构变化（例如「并入 Story ID」改成选择列表）单列，不算纯文案。

## 判据（本 Proposal 的核心产出）

六条规则：R0 是维护者给的命名判据，R1–R5 是执行规则。R0–R4 可以由人或 Agent 逐句判定，R5 必须验证。

| # | 规则 | 判定方式 | 反例 → 应改成 |
| --- | --- | --- | --- |
| **R0** | **展示名忠实于架构含义**（维护者 2026-09-15 判据）：仓库已给过用户词的概念（信息条目、话题、热点等）用已定用户词；尚未定用户词的架构术语（`Story`、`Entity`），保留术语本身而不硬造中文名——任何中文改写都会把含义改窄。禁止为了顺口而换一个更亲切但不准的词 | 逐词追问「这个名字是否覆盖该概念的全部形态」 | 「事件」用于 `Story`（只有 event kind 是事件，document/media/thread 不是）；「人物与机构」用于 `Entity`（漏掉产品/项目/地点/模型） |
| **R1** | 界面用词服从已定的用户术语：仓库已经给过中文用户名的概念，界面必须用中文名 | 对照术语表逐词检查 | `Entry` → 「信息条目」；`Spotlight` → 「热点」；`Topic` → 「话题」 |
| **R2** | 用户看不到、也操作不了的东西，名字不出现在界面上 | 逐句检查是否在说系统内部机制 | 「受管理 subtype」「未注册」「历史壳」「审计」「Revision」→ 只描述用户能做什么（「这条内容已经被你拆分成几条，原来的记录还留在这里」） |
| **R3** | 不要求用户输入或背诵内部标识符 | 检查每个输入框的期望输入 | 「并入本 Story 的 Story ID」→ 搜索选择框 |
| **R4** | 每个按钮说明「点了会发生什么」，风险动作要说明可逆性 | 逐个动作检查 | 「移除」（不可逆？可恢复？）→ 明确「移除后可恢复」或「此操作不可撤销」 |
| **R5** | 界面上每一句承诺，都能指出实现它的界面位置 | 逐句追问「这句话在哪落地」 | 「可在收藏列表快速找回」→ 收藏列表不存在，则这一句必须删掉或先把界面补上 |

R0 的实际作用是把「改成什么」从口味问题变成可判定问题：**先看仓库有没有定过用户词，再看中文改写会不会丢失含义**。它同时解释了一个看起来不一致的地方——为什么 `Topic` 要写成「话题」（仓库定过），而 `Story` 建议保留英文（仓库没定过用户词，且中文改写都会改窄）。

配套两条**检查方法**（一条能自动化，一条不能，不要互相替代）：

- **能自动化的**：术语表转成禁用词清单（内部概念名 → 建议替换词），对用户可见文案做一次扫描并列出命中位置。它只能抓 R1/R2 的一部分，抓不到「句子难懂」和「承诺与界面不符」。
- **不能自动化的**：逐屏人工评审，按上面四条规则逐句过。这一层必须由你抽查，因为「够不够白话」是产品判断。

## 方案与取舍

### 方案 A（推荐）：先出术语对照表，再分批逐屏改

1. **产出术语对照表**：一页纸，「现在界面上用的词 → 建议改成什么 → 依据（已定术语 / 需要你裁定）」。你要能一次看完并逐行裁定，不读代码、不读界面。
2. **你裁定新词**：表里凡是仓库没定过用户词的架构术语，由你敲定（2026-09-15 已全部裁定，见[术语对照表](#术语对照表-v1已逐行裁定)），然后写进术语表——**新词先入表再进界面**，防止 agent 每次即兴造词。
3. **按屏分批改**：每批一个可验收切片（例如「Story 抽屉一批」「看板与首页一批」「Topic/Entity 页一批」），每批附改动前后对照供你抽查，且与界面职责重划的切片**同批**进行（要删的表单不浪费文案改动）。
4. **同批改定位器**：每批改动同时更新按文案定位的浏览器断言，保证套件持续为绿（见[影响](#影响)）。

**取舍**：批次多、周期长，但每一步都能验收、能回滚，你也看得懂每次在改什么。代价是它依赖你的裁定节奏——裁定慢，整体就慢。

### 方案 B：只做禁用词替换（把内部概念名机械换掉）

把 `Story`/`Entity`/`Topic`/`Entry`/`Spotlight` 等词换成中文名，其余不动。

**放弃理由**：它只碰 R1，抓不到三类真问题——「并入本 Story 的 Story ID」要用户手输 ID（不是换词能解决的）、「引文」这种专业近义词（不在禁用词表里）、「可在收藏列表快速找回」这种空头承诺（换词后依然是假的）。做完之后你会觉得「改了一堆词但还是不好懂」。

### 方案 C：全局重写所有界面文案

**放弃理由**：无边界、无法验收、无法回滚，且和界面职责重划互相覆盖——被删掉的区块上的文案改了等于白改。这条是本次要避免的结果，列出来是为了说明为什么不选它。

## 这件事该走 Proposal 还是治理类任务（你要求我给建议）

**建议：判据走 Proposal（本文），实施走 G 系列治理任务。**

理由：

- 判据部分命中[准入决策表](../standards/repository-workflow.md#准入决策表)的 Proposal 触发条件——「新增或改变用户可观察行为」（文案就是用户可观察行为）与「存在两个以上长期方案，需要记录取舍和放弃原因」（上面 A/B/C 三条）。而且判据要写成长期规则（以后所有 UI 文案都遵守），这会改到稳定文档；稳定文档变更按表需要先有 accepted 的 Proposal。
- 实施部分形状更像 G 系列治理任务：跨很多文件、重复、机械中带判断、不新增功能，与 G01（文档拆分）、G02（storage-prisma 治理）同类。好处是它可以分批推进而不占产品 Task 编号，也不会被误认为一个「新功能」。

**不这么做的代价**（即备选方案与放弃理由）：如果完全不写 Proposal，直接把「改文案」当一个 Task 做，判据会变成 Agent 的私有标准——没有评审、没有裁定记录，下一个人（或下一个 Agent）无法知道为什么某个词不能用。这正好违反了「解释、取舍和重命名进入 PRD、Proposal、架构或 Task」的既定顺序。

## 术语对照表 v1（已逐行裁定）

这是本文的核心交付物：把维护者的判据（R0）算成一张表并逐行裁定完毕。A/B/C/D 四组可以直接执行；E 组已裁定处理方式，仍等「分类」的概念本身被定义。

### A. 仓库已定过用户词——直接执行，无需裁定

依据是 [`CONTEXT.md`](../../CONTEXT.md)「当前命名结论」与 Phase 1/2 已落地的界面用词。这些是**改动量最大的一批**（`Entry`/`Topic`/`Spotlight` 等现在都以英文出现在界面上）。

| 内部术语 | 架构里的实际含义 | 界面展示名 | 依据 |
| --- | --- | --- | --- |
| `Entry` | 用户可单独阅读、收藏、标注、引用的一条来源内容，必须有来源身份但不要求有 URL | 信息条目 | 命名结论 1 |
| `Topic` | 用户为持续理解某个问题建立的关注范围，只收录 Story | 话题 | 命名结论 3 |
| `Spotlight` | 某个对象在一段时间内获得高关注展示的**结果**，不是内容类型 | 热点 | 命名结论 4 |
| `Timeline` | 按时间展示更新的**视图**，不是与 Story/Topic 并列的聚合实体 | 时间线 | 命名结论 4 |
| `Feed` | 按分类、查询或推荐策略排列的连续浏览结果，不是内容副本 | 信息流 | CONTEXT.md §核心语言 |
| `Workspace` | 长期存在、可更新、可交互的体验单元（Phase 3 才出现） | 按 kind 显示「栏目」「专题」「学习计划」「工作区」 | 命名结论 5 |
| `Artifact` | 用户/系统/Agent 生成的一次可保存结果，版本化输出（Phase 3 才出现） | 产物 | CONTEXT.md §核心语言 |
| `Board` / `Section` / `Block` | 摆放结构；不拥有底层内容 | 看板 / 分区 / 区块 | ADR-0010，界面已一致 |
| `Label` / `Collection` / `Saved View` / `Annotation` / `Source` | 用户的命名分类 / 命名集合（成员为 Story）/ 持久化查询条件 / 绑定对象的用户笔记 / 从哪获取什么 | 标签 / 收藏夹 / 已保存视图 / 批注 / 来源 | Phase 1/2 界面已一致 |

### B. 架构术语——**已裁定**：只保留 `Story` 和 `Entity`

维护者 2026-09-15 裁定「只保留 `Story` 和 `Entity`」：这两个词有完整含义、中文改写必然改窄，保留原文；其余三行含义单一，换中文不损失含义（符合 R0）。

| 内部术语 | 架构里的实际含义 | 界面展示名 | 为什么不能改成更顺口的词 |
| --- | --- | --- | --- |
| `Story` | 上层**规范内容单元**；kind 含 event/document/media/thread，单 Entry 也是合法 Story | **保留 `Story`**，首次出现处给一句解释 | 「事件」只覆盖 event kind，「文章」只覆盖 document/media，「内容」又会和「信息条目」混。中文侧唯一准确的「内容单元」比英文更抽象 |
| `Entity` | 可被 Story 关联的实体（人物/组织/产品/项目/模型/地点），且实体之间有关系 | **保留 `Entity`** | 「人物与机构」漏掉产品/项目/地点/模型 |
| `Revision` | Story 的不可变版本；历史引用固定指向当时的版本 | 版本 | 含义单一，无需保留英文 |
| `kind` / `subtype` | kind 是内容形态（event/document/media/thread）；subtype 是注册表扩展的细分 | 类型 / 细分类型 | 界面已用「Story 类型」指 kind；subtype 现在裸写英文 |
| `evidence_for` / `mentions` | 一个 Story 的条目被其它 Story 当作证据引用 | 引用关系 | 「证据」是领域内部词，实际语义是跨 Story 的引用 |

### C. Topic 成员角色的六个展示名——**已裁定**：按下列替换

维护者原话「只改口语名，这里类似与过于术语化」，即问题不在数量而在词本身；随后裁定**替换**为下列口语名：

| 枚举值 | 原来显示 | 替换为 | 替换理由 |
| --- | --- | --- | --- |
| `core` | 核心 | 核心内容 | 「核心」单独出现时没说清核心什么 |
| `update` | 进展 | 最新进展 | 保留原意，补足是「新发生的那一条」 |
| `background` | 背景 | 背景资料 | 同上 |
| `analysis` | 分析 | 分析解读 | 「分析」既是名词也是动作，容易和「批注/想法」混 |
| `counterpoint` | 反方 | 不同看法 | 「反方」是辩论词，用户会以为必须是对立观点 |
| `tutorial` | 教程 | 使用教程 | 说清是「怎么用」的教程，与「教程类内容」区分 |

### D. 用户可见文案中禁止出现的内部词（按 R2 执行，无需裁定）

## 影响

- **数据**：无。文案改动不触碰数据库、不新增字段。
- **接口**：无合同变化。少数改动会顺带改界面结构（例如 R3 的「并入 Story ID」改成选择列表），那部分需要读取「可作为归并目标的 Story 列表」——**这是唯一可能要加只读查询的地方**，归界面职责重划的 Task 评估，不在纯文案批次里夹带。
- **测试（本次最实际的影响）**：浏览器验收大量按界面文字定位。目前 5 个 spec 文件（`e2e/browser/`）里共有 **205 处**按文案定位的断言（`getByLabel` / `getByPlaceholder` / `getByText` / `getByRole(..., { name })`），其中 `phase2-organization.spec.ts` 一个文件就有 100 处左右。**结论：文案改动必须与定位器同批修改**，且每批都要重跑浏览器套件；否则套件转红会被误判成功能回归（本仓库 2026-09-15 刚出现过一次间歇失败，对红灯的解读已经很敏感，不宜再叠加噪声）。
- **安全**：无变化，不涉及权限、Secret 或不可信输入。
- **迁移/回滚**：无数据迁移。回滚 = 代码回滚；文案改动不产生数据副作用。唯一的回滚残留是「用户已经习惯的新词」，所以术语一旦裁定就不要反复改。
- **发布**：不涉及发布部署（既有后置债）。

- **判据可执行**：拿 5 句当前界面文案做盲测，按 R1–R5 能得出一致结论（谁判定都一样），证明判据不是「看感觉」。
